# preview v0.2, step 4: the operator's filaments and the customer's feedback, implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the customer tries the operator's filaments on each part (the 3D view recolours live) and sends their colour wishes and a
comment back; the operator gets a mail, sees it next to the version in the web app and over MCP; the customer sees what they sent.

**Architecture:** two tables, `filaments` and `feedback` (appended migrations), each with its domain module (`backend/filaments.ts`,
`backend/feedback.ts`) mirrored on MCP and REST. The customer's send is a server action of the customer pages that starts from
`customerByToken` (`sendFeedback(rt, token, …)`), validated against the version's facts and the available filaments, limited per
customer. The mail goes through the configured SMTP (`backend/mail.ts`, nodemailer, injectable as `rt.sendMail`).

**Tech Stack:** Next.js 16, next-app-kit, SQLite (kysely + better-sqlite3), nodemailer, vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-27-preview-v0.2-design.md` (goal 7, "The operator's filaments", "Feedback").

## Global Constraints

- Filament: name (1–60), material (1–20, as written, e.g. PLA), colour `#rrggbb`, available yes/no, position. MCP `list_filaments`,
  `create_filament`, `update_filament`, `delete_filament`; REST mirrors them.
- The picker offers the available filaments plus "wie im Entwurf"; no filaments defined: no pickers, no colour part of the feedback,
  the comment still works. The Druck card names a filament from the list when colour and material match an entry exactly.
- Feedback: per version; customer, time, comment (≤ 2000 characters, optional), wishes `[{part, filament}]` validated against the
  version's facts and the available filaments; at least one of the two. 10 per customer per hour, 50 per day. One gate:
  `customerByToken`, a version that isn't the customer's is refused like an unknown one.
- Mail to `PREVIEW_FEEDBACK_EMAIL` (optional; unset: no mail) through `PREVIEW_SMTP_URL` / `PREVIEW_SMTP_FROM`: model, version,
  the wishes as a list, the comment, a link into the web app. No customer email is collected. A failed mail never loses the feedback.
- Web app: each version's feedback on the model page, newest first, marked seen when shown; the unseen ones on the start page.
  MCP/REST `list_feedback` (customer, model, unseen), `mark_feedback_seen`.
- The customer page shows their own sent feedback under the version, read-only.
- Logs: no token, link token, file name, email address or comment text.

## Review Focus

- A wish for a part key the version doesn't have, or a filament that is unavailable or deleted: refused, nothing stored.
- A filament deleted after a wish named it: the stored feedback still says which (name, material, colour are copied into the wish).
- The 11th feedback within an hour: refused with the German message, nothing stored, no mail.
- SMTP down: the feedback is stored, the customer is told it arrived, the failure is logged without the address.
- Another customer's model or version number in the form: refused like a missing one.
